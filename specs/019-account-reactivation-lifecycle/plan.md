# Implementation Plan: Account Reactivation & Lifecycle Management

**Branch**: `019-account-reactivation-lifecycle` | **Date**: 2026-08-15 | **Spec**: [specs/019-account-reactivation-lifecycle/spec.md](file:///c:/Users/amend/Dev/sistema-contable/specs/019-account-reactivation-lifecycle/spec.md)

**Input**: Feature specification from `specs/019-account-reactivation-lifecycle/spec.md`

## Summary

Implement comprehensive account lifecycle management, including one-click account reactivation (`ACTIVE` / `INACTIVE`), strict deletion protection blocking physical removal of accounts with historical journal entries (enforcing GAAP/IFRS ledger immutability), transaction combobox filtering to omit inactive accounts from new data entry, and historical reporting continuity.

## Technical Context

**Language/Version**: TypeScript 5.x, Node.js 20+  
**Primary Dependencies**: NestJS 10.x, TypeORM 0.3.x, Next.js 14+ (App Router), React 18, TailwindCSS v4.3, Lucide Icons, Zod  
**Storage**: PostgreSQL with relational constraints (`accounts`, `journal_entries`, `transactions`, `account_period_balances`)  
**Testing**: Jest (NestJS unit & integration tests), React Testing Library (frontend component tests)  
**Target Platform**: Modern Web Browsers (Desktop & Mobile responsive) / Node.js backend  
**Project Type**: Monorepo Web Application (`backend/`, `frontend/`, `shared/`)  
**Performance Goals**: Account status updates & reactivation response in <100ms; reactive UI state updates in <2 clicks  
**Constraints**: 100% GAAP/IFRS audit trail preservation; zero orphaned transactions; strict ESLint compliance (zero errors/warnings); 100% test coverage on financial calculation/validation engines  
**Scale/Scope**: `UpdateAccountUseCase`, `DeleteAccountUseCase`, `AccountController`, `AccountsManagePage`, `AccountsList`, `JournalEntryRow`, `TransactionModal`, `BudgetAccountModal`, `@sistema-contable/shared`

## Constitution Check

_GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design._

- [x] **I. Double-Entry Bookkeeping & Ledger Integrity**: Pass — Physical deletion of accounts with $\ge 1$ journal entries is strictly blocked (HTTP 400), guaranteeing append-only immutable ledger integrity and referential consistency.
- [x] **II. Clean Architecture & SOLID Principles**: Pass — Use cases (`UpdateAccountUseCase`, `DeleteAccountUseCase`) encapsulate lifecycle rules using Dependency Injection. Domain entities and use cases remain decoupled from framework presentation.
- [x] **III. Monorepo Organization & Unified Type Safety**: Pass — `AccountStatus` enum, request DTOs (`UpdateAccountRequestSchema`), and responses are centralized in `shared/src/index.ts`.
- [x] **IV. Budgetary Control and Personal/Family Domain**: Pass — Inactive accounts are excluded from active budget creation/allocation while preserving past budget execution history.
- [x] **V. Strict Test-Driven Development (TDD) & Quality Verification**: Pass — Unit tests for use cases, integration tests for deletion guards and reactivation, and component tests for UI buttons and combobox filtering will be developed and verified before merging.
- [x] **VI. Prevention of Magic Strings & Strict Type Constants**: Pass — Account statuses (`ACTIVE`, `INACTIVE`) and accounting roles are strictly typed via TypeScript enums and Zod schemas without inline magic strings.
- [x] **VII. Mandatory ESLint Compliance & Static Code Quality**: Pass — All modified backend, frontend, and shared code must pass ESLint with zero errors and zero warnings.
